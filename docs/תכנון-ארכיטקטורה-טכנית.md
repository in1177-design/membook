# תכנון ארכיטקטורה טכנית — כלי איסוף תמונות/טקסטים לאלבומי ברכה

## 1. סקירה כללית

מוצר בעומס נמוך ולא-רציף (עומס גבוה סביב כל אירוע, שקט בין לבין), עם שלוש חזיתות משתמש:

- **אפליקציית ניהול (אדמין)** — לשימוש הסטודיו בלבד: ייבוא רשימת מוזמנים, שליחת לינקים, מעקב, הורדת חומרים.
- **עמוד מוזמן ציבורי** — עמוד אחד לכל טוקן ייחודי, פשוט ביותר, חייב לעבוד בלי תקלות בנייד (Safari/Chrome), בלי התחברות.
- **Backend/API** — אחראי על מודל הנתונים, אימות טוקנים, ניהול ההעלאה, שליחת Twilio וייצוא.

**המלצה**: אפליקציית Next.js אחת עם שני נתיבים (`/admin/*` מוגן, `/i/[token]` ציבורי), מסד נתונים Postgres יחיד, ו-Cloudinary לכל המדיה. כך כל הפרויקט הוא ריפו אחד, פריסה אחת, מסד נתונים אחד — מתאים לבנייה עצמאית/צוות קטן.

```
Next.js App (Vercel)
 ├─ /admin/*  — ניהול פרויקטים, ייבוא CSV, טבלת מוזמנים, שליחה חוזרת, הורדת הכל
 ├─ /i/[token] — עמוד ציבורי: שליפת השאלה לפי טוקן, טופס העלאה
 └─ /api/*     — נתיבי projects/invitees/submissions/import/dispatch, חתימת Cloudinary, שליחת Twilio
        │
   Postgres (Neon/Supabase) — projects, invitees, links, submissions
   Cloudinary — אחסון תמונות, טרנספורמציות, CDN
   Twilio — שליחת WhatsApp/SMS בלבד (לא בוט)
```

## 2. הטכנולוגיה המומלצת

| שכבה | בחירה | למה |
|---|---|---|
| Frontend + Backend | Next.js (App Router), TypeScript | פריימוורק אחד, פריסה אחת, קל לבנות מהר לבד |
| אחסון | Vercel | פריסה ללא תצורה, מתאים לעומס נמוך ומשתנה |
| מסד נתונים | Postgres (Supabase/Neon) | מודל היחסים (פרויקט→מוזמן→שליחה) הוא יחסי מטבעו |
| ORM | Prisma | מיגרציות מהירות, טיפוסים בטוחים — מתאים לסכימה שתשתנה תוך כדי משוב |
| מדיה | Cloudinary (כבר קיים) | העלאה, ולידציה, CDN — בלי לבנות פייפליין תמונות בעצמכם |
| מסרים | Twilio (כבר קיים) | WhatsApp+SMS מ-API אחד, מופעל רק ע"י הסטודיו |
| אימות אדמין | סיסמה משותפת / allowlist אימייל פשוט | אין צורך במערכת הרשאות אמיתית עדיין |

## 3. מודל נתונים

עיקרון מנחה: לכל טבלה יש כבר `project_id`, כדי שכשתגיע גרסת B2B יתווסף `organization_id` מעל, בלי לשנות מבנה קיים.

- **projects** — אירוע (שם, סוג אירוע, פרטי לקוח, תאריך אירוע, סטטוס, השאלה הקבועה לפרויקט)
- **invitees** — מוזמן (שם, טלפון/מייל, קרבה, שאלה מותאמת אישית אופציונלית)
- **invite_links** — הטוקן עצמו, מופרד מזהות המוזמן כדי לאפשר ביטול/יצירה מחדש (סטטוס, תוקף, זמן צפייה אחרון)
- **submissions** — הטקסט שנשלח, סטטוס (ממתין/הושלם/מסומן לבדיקה)
- **media_assets** — טבלה נפרדת (יחס אחד-לרבים) כדי לספוג בקלות מעבר מ"תמונה אחת" ל-2-3 תמונות בעתיד, בלי שינוי סכימה

## 4. לינקים אישיים — אבטחה

- טוקן אקראי קריפטוגרפית, לפחות 22 תווים (128 סיביות אנטרופיה) — לא UUID נגזר מה-ID, לא רציף, לא מבוסס שם/טלפון.
- כתובת ה-URL לא חושפת מזהה או מידע מזהה.
- **אין התחברות/סיסמה** — הטוקן עצמו הוא "האישור", כמו לינק שיתוף של Google Docs. סביר כי התוכן (תמונה/הודעה אישית) רגיש בינוני, לא פיננסי/רפואי.
- מותר לערוך מחדש עד סגירת הפרויקט (לא נעילה לאחר שליחה ראשונה) — משפחות ירצו לתקן טעות/להחליף תמונה.
- תוקף נגזר מתאריך האירוע + חלון חסד, לא TTL קבוע מרגע היצירה.
- ביטול לינק אפשרי בלי מחיקת היסטוריית המוזמן; הגבלת קצב (rate limiting) על נקודת הכתיבה בשרת כהגנה מפני שימוש לרעה.

## 5. תהליך ההעלאה

בצד הלקוח: אימות ראשוני (סוג קובץ כולל HEIC לאייפון, גודל עד ~15MB, אורך טקסט), שגיאות ברורות בעברית פשוטה (קהל היעד כולל אנשים לא טכניים). ההעלאה עצמה ישירות מהדפדפן ל-Cloudinary דרך חתימה קצרת-טווח מהשרת (לא דרך ה-serverless function שלכם) — כך נמנעים ממגבלות זמן/גודל של פונקציות serverless.

בצד השרת: אימות חוזר על כל הפרמטרים, כתיבה טרנזקציונית של submission + media_asset, וסימון הלינק כ"נשלח". טיפול מפורש בשגיאות: טוקן לא תקף (עמוד ידידותי, לא קריסה), כשל/timeout בהעלאה, שליחה כפולה (מוחלפת ולא נערמת).

## 6. תהליך ניהול (אדמין)

שכבת CRUD+סטטוס דקה: רשימת פרויקטים, ייבוא CSV עם מסך אישור לפני commit (תפיסת טעויות מיפוי כותרות), טבלת מוזמנים עם סטטוס לינק (לא נשלח/נשלח/נפתח/הוגש/פג תוקף), כפתור שליחה/שליחה חוזרת בודד ומרוכז דרך Twilio, הורדת הכל כ-ZIP + CSV/JSON לטקסטים, צפייה בהגשה בודדת.

## 7. Twilio — שימוש

שימוש חד-כיווני בלבד (סטודיו ← מוזמן), לא בוט שיחה. פעולת "שליחה" באדמין קוראת ל-API של Twilio (WhatsApp/SMS) עם תבנית מאושרת מראש. חשוב: WhatsApp עסקי דורש אישור תבנית הודעה מ-Meta — שלב חד-פעמי חיצוני, לא תלוי בטוויליו, כדאי להתחיל בו מוקדם כי זמן האישור לא בשליטתכם. SMS הוא נתיב חלופי זהה בקוד אם האישור מתעכב.

## 8. פריסה ואחסון

Vercel (אפליקציה), Supabase/Neon (מסד נתונים מנוהל עם גיבויים — שווה את התשלום החודשי בהתחשב באופי הנתונים החד-פעמי/הרגשי), Cloudinary ו-Twilio ללא תשתית נוספת. סביבת production אחת מספיקה בשלב זה; preview deployments מול מסד נתונים נפרד לבדיקות.

## 9. פרטיות ושמירת מידע

כדאי מדיניות פשוטה אפילו ברמת MVP: כמה זמן שומרים מדיה/טקסט אחרי שהפרויקט "נמסר", ופעולת "מחיקת נתוני פרויקט" ידנית באדמין (מחיקה מ-Postgres וגם מ-Cloudinary). מבנה ה-foreign keys הנקי הופך מחיקה לפי פרויקט לפשוטה יחסית.

## 10. נקודות הרחבה עתידיות (לא נבנות עכשיו)

- **שיבוץ אוטומטי לתבנית** — תוסף נקי כי הנתונים כבר מובנים לפי פרויקט.
- **B2B/הרשאות/חיוב** — ה"תפר" (`organization_id`) כבר מוכן מעל projects; לא צריך לשכתב סכימה.
- **בדיקת איכות תמונה ב-AI** — נקודת חיבור טבעית מיד אחרי העלאת Cloudinary.
- **אפליקציית מובייל** — כל הלוגיקה מאחורי `/api/*`, כך שאפליקציה עתידית (סביר שלצוות הסטודיו, לא למוזמנים) יכולה להשתמש באותו API.
- **הערה על יתרון תחרותי**: הטכנולוגיה הזו לא אמורה להיות קשה להעתקה — המוקד האמיתי (שירות, עיצוב, אמון) נמצא מחוץ לקוד, אז אין טעם להשקיע יתר על המידה בהגנה טכנית.

## 11. הערכת מאמץ בנייה (בונה יחיד/צוות קטן, כל הכלים כבר נבחרו)

| חלק | הערכה |
|---|---|
| שלד פרויקט, סכימה, פריסה | 0.5–1 ימים |
| אדמין: CRUD פרויקטים + ייבוא CSV + טבלת מוזמנים | 1.5–2 ימים |
| טוקן/לינק + עמוד מוזמן ציבורי + ולידציה | 1.5–2 ימים |
| אינטגרציית Cloudinary + מצבי שגיאה | 1–1.5 ימים |
| API הגשות + מסך סטטוס + ייצוא/ZIP | 1–1.5 ימים |
| שליחת Twilio (כולל הגשת תבנית ל-Meta) | יום פיתוח + זמן המתנה חיצוני לאישור |
| ליטוש: עברית/RTL, בדיקה על מכשירים אמיתיים, מצבי ריק/שגיאה | 1–2 ימים |
| **סה"כ פיתוח** | **כ-8–11 ימי עבודה** |

זמן הלוח השנתי בפועל ארוך יותר בגלל זמן אישור Meta ומשוב מהסטודיו עצמו — כדאי לתכנן כ-2–3 שבועות קלנדריים מקיק-אוף ועד ריצה על פרויקט לקוח אמיתי ראשון, גם אם זמן העבודה בפועל פחות משבועיים.
